# ops-support Part 2: MCP Server — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `ops-mcp` in its MVP mode, `operational-support`: a stdio MCP server whose tools let a client go from a problem statement to a root cause and proposed fix: graph and code navigation, logs from compose/Kubernetes/files mapped to code, configuration checks, read-only PostgreSQL and Redis access, LSP lookups, execution-flow analysis (error paths, request timelines, queue hops, table access, recent git changes, blast radius, rollout history), a semantic layer that the client reads and writes (with search by meaning), incident reports saved as files, and agent playbooks as MCP prompts.

**Architecture:**
- Tool logic lives in `engine` modules so it can be tested without MCP: `codeq`, `telemetry`, `search`, `logs`, `runtime`, `logmatch`, `flow`, `timeline`, `cfgcheck`, `changes`, `datastore`, `lsp` and `incidents`.
- `services/mcp` is a thin `rmcp` 3.7 adapter: one struct `OpsServer { root: PathBuf }` with `#[tool_router]` and `#[prompt_router]`.
- Each tool call reloads `Ctx` (so config edits apply live), connects to whatever backend it needs, and returns JSON text. Every output passes through `redact`.

**Tech Stack:** rmcp 3.7 (features `server`, `transport-io`, `macros`; use `rmcp::schemars`), tokio, sqlx 0.9 (`runtime-tokio`, `tls-rustls`, `postgres`, `json`), redis 1.8 (`tokio-comp`), `kubectl` and `docker` CLIs as subprocesses, plus everything from Part 1.

**Spec:** `docs/superpowers/specs/2026-10-24-ops-support-design.md` and `docs/superpowers/specs/2026-10-24-persistence-and-semantic-layer-design.md` ("the layer design"), and `docs/superpowers/specs/2026-10-24-execution-flow-and-investigation-tools-design.md` ("the flow design") · **Depends on:** `docs/superpowers/plans/2026-10-24-ops-indexer.md` (Tasks 0–7d)

## Global Constraints
- Tools return `Result<String, String>`. `Ok` is pretty JSON. `Err` is a one-line redacted message. A tool never panics.
- The server starts and answers `tools/list` with Memgraph, Postgres, Redis, Docker and kubectl all unavailable.
- Output caps: logs 2,000 lines / 256 KiB per call; SQL 200 rows; Redis values 4 KiB each; `read_file` 400 lines; `graph_query` 500 records.
- Arguments from the LLM are never interpolated into a shell. Subprocesses use argv (`tokio::process::Command`), and placeholders replace whole arguments.
- `since` accepts `^\d+[smhd]$`, capped at `7d` for logs. `recent_changes` accepts `^\d+[dhw]$`, capped at `90d`.
- `git`, `docker` and `kubectl` run only as argv, with read-only subcommands: git `rev-parse log show status`; kubectl `get logs`; docker `compose ps|logs`, `inspect`. `GIT_TERMINAL_PROMPT=0` is set. Diff text is never returned.
- Kubernetes namespaces must be in `kubernetes.namespaces`. Anything else is rejected before `kubectl` runs.
- **Modes:** `ops-mcp --mode <mode>`. This plan implements `operational-support` only, and it is the default. Every tool and prompt in this plan belongs to that mode. The spec's other modes (`developer-support`, `operational-onboarding`, `developer-onboarding`) are out of scope here, and their names are rejected with "mode not available yet".
- `ops-mcp` writes nothing to stdout but MCP protocol messages. Every tool runs through `run_tool` (Task 8a), so it is audited.
- The semantic tools (Task 8b) belong to `operational-support` too; the layer design puts them in every mode. Memgraph writes from MCP happen **only** through `remember`/`revise`/`retract` and `reindex`. `graph_query` stays read-only.
- Tool names and parameters are exactly as written in this plan. Each tool's description says what it returns and when to use it.

## Review Focus
1. **Backends down at startup.** The server must still list all tools, and a tool call must return an error string, not crash. Test: `smoke_lists_tools_with_backends_down` (Task 8).
2. **Secrets in errors.** A Postgres connection failure must not echo the URL's password. A compose `environment` containing `PASSWORD=` must come back masked from `service_config`. Tests: `pg_error_has_no_password` (Task 12), `service_config_redacts` (Task 11).
3. **Write attempts through read tools:** `WITH d AS (DELETE …) SELECT 1`, `SELECT 1; DROP TABLE x`, lowercase `merge (n)` in Cypher, `CALL` procedures, Redis `FLUSHALL`/`CONFIG SET`/`EVAL`. Tests: `pg_rejects_writes` (Task 12, ignored), `cypher_guard` (Task 8), `redis_allowlist` (Task 12).
4. **Multi-line Python tracebacks** must map to the function and line that raised. They must not become dozens of unmatched lines. Test: `traceback_frames_resolve` (Task 10).
5. **A log directory that isn't writable**, or a client that never sends `logging/setLevel`, must not break tool calls or put log text on stdout. Test: `logging_never_breaks_protocol` (Task 8a).
6. **A heuristic hop presented as certain**: every `error_paths` hop must carry its `match` label (`exact`, `by_name`, `catch_all`, `unknown`). Tests: `caught_and_reraised_as_http` asserts `CatchAll`, and `serializes_like_spec` pins the JSON (Task 10b).
7. **Two clients at once** (Claude Code and Copilot CLI each running `ops-mcp`): concurrent `remember` calls must both land, and `reindex` while `ops watch` runs must report "index in progress" instead of corrupting anything. Tests: `concurrent_remember` (Task 8b, ignored), `reindex_reports_lock` (Task 8).
8. **Namespace outside the allow-list**, or a `since` like `1m; rm -rf /`, must be rejected before any process starts. Test: `k8s_namespace_and_since_rejected` (Task 9).

- Produces:
  - `codeq::cypher_is_read_only(q: &str) -> bool`: rejects (case-insensitive, whole-word) `CREATE MERGE DELETE DETACH SET REMOVE DROP LOAD FOREACH CALL`, outside string literals. `// ponytail: keyword guard; the graph is rebuildable from source. Use a read-only Memgraph role if Enterprise auth is available.`
  - `codeq::{service_map, find_symbol, code_context, trace_flow}`: `async fn(ctx: &Ctx, …) -> Result<serde_json::Value>`, each one fixed Cypher query.
  - MCP tools, with params as `#[derive(Deserialize, JsonSchema)]` structs:
    - `service_map(focus: Option<String>, direction: Option<String> /* dependents (default) | dependencies | both */, depth: Option<u8> /* 3, max 6 */)`.
      - Without `focus`: services, datastores, queues and tables with kind/language/framework, every BOUNDARY edge with its `via` and `evidence`, plus USES_DATASTORE.
      - With `focus` (service, datastore, queue or table, by id or name): the blast radius, per flow design §6. It follows `BOUNDARY` (consumer → provider), `USES_DATASTORE`, `SENDS_TO`/`RECEIVES_FROM` and `READS_TABLE`/`WRITES_TABLE`, and gives each node its shortest path and the hop `via`s.
    - `contract(name: String)`: the contract's kind and path, provider, consumers, endpoints (each with its implementing route and handler function, or `unimplemented`), schemas with the functions that use them, and consumer HTTP calls that match no declared endpoint (`undeclared_calls`). This shows drift at the boundary.
    - `find_symbol(name: String, service: Option<String>, kind: Option<String>)`: up to 50 matches on `name` or `qualname` containing `name`, each with `{id, kind, name, owner, service, file, start_line}`.
    - `code_context(id_or_name: String)`: the symbol's source (read from disk via `ctx.abs`), its callers and callees (1 hop), routes it handles, log statements, env reads, and CALLS_API targets.
    - `trace_flow(id_or_name: String, direction: "up"|"down", depth: Option<u8> /* default 4, max 8 */)`: paths over `CALLS|HANDLED_BY|CALLS_API|TEMPLATE_BINDS|SENDS_TO→RECEIVES_FROM`. "up" ends at entrypoints or routes; "down" ends at leaves.
    - `read_file(path: String, start: Option<usize>, end: Option<usize>)`: the canonicalized path must fall under a configured service, shared-lib or contract path, or be one of the compose files or service Dockerfiles. Paths whose name starts with `.env`, anything under `.ops/`, and `ops.yaml` itself are always denied, even inside an allowed path. Redaction only masks secret-looking keys, so allow-listing paths is the real protection.
  - `codeq::allowed_path(ctx: &Ctx, path: &str) -> Result<PathBuf>`: the rule above. Task 13's `lsp(file)` uses it too.
    - `graph_query(cypher: String, params: Option<serde_json::Map>)`: guarded, capped.
    - `reindex()`: `store::index(ctx, Incremental, wait = 0)` in `spawn_blocking`. Returns the `IndexReport`, or the lock's "index in progress (pid N, since T)" as an error.
  - `codeq::staleness(ctx) -> Result<Staleness { last_run_at: Option<String>, files_changed_since: usize }>`: counts workspace files whose mtime is later than the latest `IndexRun.finished_at`, honouring `exclude`. `// ponytail: mtime check, not hashes; a touched-but-unchanged file counts as changed until the next run.`
  - `service_map`, `contract`, `code_context` and `trace_flow` each add two fields to their output:
    - `knowledge`: `semantic::about` for the nodes they return, current entries plus stale ones flagged `"stale": true`, each as `{id, kind, title, confidence, status}`;
    - `index`: `staleness`, when `files_changed_since > 0`.

Writing is append-only JSONL to `<dir>/audit.YYYY-MM-DD.jsonl`, behind one `Mutex<File>` reopened when the date changes. It's a no-op when `audit: false`. `// ponytail: one mutex-guarded file; move to a channel writer if tool calls ever run in parallel at volume`.
  - `audit::sanitize_args(v: &Value) -> Value`: redact every string, then truncate each to 2 KiB.
  - Every tool body runs inside `OpsServer::run_tool(name, args, f)`, which times the call, collects the `backends` the tool reports, writes the audit record and returns the tool's `Result<String, String>`.     - backend unreachable (warn);
    - a cap hit (warn: "rows truncated at 200");
    - a rejected namespace or command (warn).

### Task 8b: Semantic-layer tools

**Files:**
- Create: `services/engine/src/search.rs`, `services/mcp/src/semantic_tools.rs`
- Modify: `services/mcp/src/server.rs`

**Interfaces:**
- Consumes: `semantic::{create, revise, retract, get, about, NewEntry, Kind, Confidence}`, `embed::{status, embed_texts, InputKind}`, `codeq::find_symbol`, `run_tool`/`ToolCtx` (Task 8a), the `initialize` client info
- Produces:
  - `search::Hit { id: String /* the symbol or Knowledge id, never a chunk id */, label: String, score: f64, via: Vec<&'static str> /* "vector" | "text" | "near" */, match_lines: Option<(usize, usize)> /* the best chunk's line range */ }`
  - `search::aggregate(chunk_hits: &[(String /* parent id */, f64, (usize, usize))], how: Aggregate) -> Vec<(String, f64, (usize, usize))>`: `Max` keeps each parent's best chunk; `MeanTop2` averages its best two. The best chunk's lines are kept.
  - `search::rrf(lists: &[Vec<String>], k: f64 /* 60.0 */) -> Vec<(String, f64)>`: reciprocal-rank fusion, sorted by score descending, ties broken by id.
  - `search::hybrid(ctx, query: &str, scope: Scope /* Knowledge | Code */, k: usize, near: Option<&str>, filter: Filter { service: Option<String>, kinds: Vec<String>, include_stale: bool }) -> Result<(Vec<Hit>, &'static str /* "hybrid" | "text-only" */)>`:
    1. `embed_texts([query], Query)`, then `vector_search.search("chunk_vec", 5k, vec)`, if `embed::status` is `Vector`. Follow `CHUNK_OF` to parents, keeping `layer:'structural'` (Code) or `:Knowledge` (Knowledge), then `aggregate` with `semantic.embeddings.chunking.aggregate`.
    2. `text_search.search(index, "data.<prop>:<terms>")` over `title`/`body` (Knowledge), or over `card` and `chunk_text` (Code, mapping chunk hits to parents). Escape the terms, and use one query per property.
    3. RRF over the two lists. Then add `1/(60 + d)` for hits within 2 hops of `near`, where `d` is the hop count.
    4. Filter: drop `retracted`; drop `stale` unless `include_stale`; apply `service` and `kinds`.
  - `author_client`: normalized from `initialize.clientInfo.name` and stored on the server at initialize. `claude-code`, `copilot-cli`, else the raw lowercase name.
  - MCP tools (layer design §4.2):
    - `remember(kind, title, body, anchors: Vec<String>, evidence: Vec<String>, confidence, tags: Option<Vec<String>>, steps: Option<Vec<String>>, from: Option<Vec<String>>, to: Option<Vec<String>>, author_model: Option<String>)`.
      - Each anchor resolves through `find_symbol` or as an exact id. Zero or several matches is an error that lists the candidates.
      - Returns `{id}`.
    - `revise(id, title?, body?, confidence?, evidence?, anchors?)` → `{id: new_id, supersedes: id}`.
    - `retract(id, reason)`.
    - `recall(target: Option<String>, query: Option<String>, kinds: Option<Vec<String>>, include_stale: Option<bool>, k: Option<usize> /* 10, max 50 */)`.
      - `target` alone: `semantic::about(target + its 1-hop neighbours)`.
      - `query`: `hybrid(Knowledge, near = target)`.
      - Neither: an error.
      - Returns entries plus `search_mode`.
    - `knowledge_gaps(service: Option<String>, kinds: Option<Vec<String>>, limit: Option<usize> /* 25 */)`:
      - Symbols with no current `summary`, ranked by route handlers and entrypoints first, then by incoming CALLS/CALLS_API count.
      - Then every `stale` and `orphaned` entry.
    - `search_code(query, service: Option<String>, kinds: Option<Vec<String>>, k: Option<usize> /* 10, max 50 */)`: `hybrid(Code)`, each hit with `{id, label, qualname, file, start_line, match_lines}` and its current knowledge titles. `match_lines` points into long functions, at the part that matched.
  - Every write tool reports backend `"memgraph"`, and its audit record keeps `title` and `kind` in `args`. `body` is redacted and truncated like any other argument.

  - **JSON shape is exactly flow design §1.3.** The spec's keys are Rust keywords, so rename: `type_name` → `type`, `in_fn` → `in`, `matched` → `match`. `Outcome` serializes as one string (`"handled"`, `"logged"`, `"swallowed"`, `"propagates"`, `"reraised_as HTTPException"`), through a custom `Serialize`. `Match` and `ResultKind` are snake_case strings (`catch_all`, `http_status`). `None` fields are omitted. The escaping route's service selects its own handler map. This is the algorithm in flow design §1.2: 20 hops per path, 50 paths, escaping paths sorted first.
  - `flow::load(ctx, target_ids, depth) -> Result<FlowGraph>`. It follows flow design §1.2 step 1:
    - **Down:** the target's callees up to `depth`. Every function there with `raises` is a start.
    - **Up:** the caller closure of all those functions up to `depth`, with `CALLS.lines`.
    - Plus every exception class's `bases`, and the `handles_exception` handlers grouped by service.

    `error_paths("pay")` or its route therefore finds the raise in `charge`. `compute` takes the start ids `load` collected.
  - MCP tool `error_paths(target: String, exception: Option<String>, depth: Option<u8>)`. `target` is a function, route or log-statement id or name. A log statement starts from its function; a route starts from its handler.
